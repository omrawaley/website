## What is an ASIC?

<BlogImage
  src="https://thumb.wikimedia.org/wikipedia/commons/thumb/1/1f/Network_traffic_processing_ASIC_inside_an_Ethernet_switch.jpg/500px-Network_traffic_processing_ASIC_inside_an_Ethernet_switch.jpg?utm_source=en.wikipedia.org&utm_campaign=parser&utm_content=thumbnail"

</BlogImage>

An ASIC (Application-Specific Integrated Circuit) is a microchip built for one specific purpose (and typically for a single customer).

Unlike a CPU, which decodes and executes software instructions (binary code), an ASIC has no operating system. All of the logic gates are hard-wired internally to perform a specific, repeated task.

As such, ASICs can be incredibly power efficient, more performant, and much smaller.

This also means that you can test ASIC designs on real hardware using FPGAs, as you can reprogram how their logic gates are connected internally.

Currently, they're used for things like:

- Bitcoin miners, since they can run hashing algorithms much more efficiently than CPUs and GPUs
- Consumer electronics, for specialized tasks like image stabilization and battery management
- Telecommunications, for high-speed packet forwarding

## Tiny Tapeout

Typically, manufacturing ASICs (and really any kind of semiconductor chip) can cost hundreds of thousands of dollars.

<img src="/images/tt02_board_top.jpeg"></img>

[Tiny Tapeout](https://tinytapeout.com) is an educational project that gives hobbyist developers access to this art by pooling together hundreds of peoples' money to get all of their designs on one unified chip. So, the manufacturing cost is split amongst everyone, each person paying their small share.

## Beginning and Limitations

Before I started my design, or thought about what I wanted to make, I first had to research the restrictions.

A 1x1 Tiny Tapeout tile on the HC design can fit roughly 1000 logic gates.

For context, if you use the tile entirely as memory, you can only fit ~320 D flip-flops, or ~40 bytes of memory.

Yikes! Not a lot to work with.

However, despite that, I had seen many incredible projects like Rick Astley's _Never Going to Give You Up_ music video (by bitluni), an audio decoder and player, and even a tiny 8-bit RISC-V CPU.

These amazing projects almost seemed to defy all limits, which gave me hope that the platform was more capable than the specifications made it seem.

## Verilog and HDLs

Before starting a project, I dug into the technologies used to design an ASIC and came to the conclusion that the best, and most industry-standard method, involves using a Hardware Description Language.

A Hardware Description Language is a bit like "coding hardware" in the sense that the "code" describes how the circuit is connected.

In other words, you are not writing a program that is read, decoded, and executed by a CPU; you are creating (or, rather, "describing") the physical circuit itself, including every logic gate and bus.

Here is a snippet of code from `ticker.v`:

```
module ticker#(
    parameter COUNT_MAX = 200000
) (
    input wire clk,
    input wire rst_n,
    output wire tick
);

    reg [17:0] count;

    assign tick = (count >= COUNT_MAX) ? 1 : 0;

    always @(posedge clk) begin
        if (~rst_n) begin
            count <= 0;
        end else if (count >= COUNT_MAX) begin
            count <= 0;
        end else begin
            count <= count + 1;
        end
    end

endmodule

```

An 18-bit register `count`, which functions like a counter, is created. It counts all the way to `COUNT_MAX`.

This snippet resembles "normal" code, especially with its C-like syntax, but underneath the surface, is is actually describing a circuit itself, where `tick` is really a wire that toggles between `0` and `1`.

Unlike traditional code, which is sequential, HDL code "runs" in parallel because it describes an entire circuit at once.

## Architecture: How it Works

Here is a block diagram representing the overarching structure of the Verilog code.

<BlogImage
  src="/images/tt-pong-asic-block-diagram.png"
  alt="Block diagram of the Verilog code"
>
  Verilog module architecture
</BlogImage>

- `ticker`: generates in-game "ticks" for the game logic, since using plain clock signals would result in super fast (nearly instant) game updates.
- `paddle`: a general game data container used by both the AI and player objects. The only difference is that the player paddle responds to the chip's input pins.
- `ball`: a game data container for the ball. It also handles collisions with screen boundaries and paddles (which is why they are inputs to the ball module).
- `vga_controller`: generates VGA blanking signals and keeps track of the current beam position.
- `renderer`: takes all of the game data containers and selects the appropriate RGB color for the specific pixel given by the VGA controller (the current beam position).

Note: "game data container" refers to something that stores data like x and y positions, width and height, etc.

## VGA

In my embedded systems work, when it comes to graphics, I've mostly only worked with I2C and SPI displays. (Besides dabbling with HDMI video on a few Raspberry Pi handhelds...)

As it turns out, the Tiny Tapeout carrier board has a module port that can accept the [Tiny VGA PMOD](https://github.com/mole99/tiny-vga), which allows the ASIC to transfer live VGA signals.

<BlogImage
  src="https://github.com/mole99/tiny-vga/raw/main/img/v1.2_pcb1.jpg"
  alt="Tiny VGA PMOD"
>
  [GitHub repo](https://github.com/mole99/tiny-vga)
</BlogImage>

I was extremely surprised by how easy it is to generate VGA signals and how simple the protocol is.

Essentially, VGA uses a scanline approach similar to the Game Boy and NES PPUs, whereby a "beam" goes through every pixel, row by row.
At certain blanking periods, such as the end of a row or the end of the last row, you emit either a HSYNC or VSYNC signal, respectively.
For each position of the beam, you just output a corresponding RGB value. Since VGA is an analog protocol, you then need to convert those
digital RGB signals into analog values, which is done trivially using a resistor ladder on the Tiny VGA PMOD.

<BlogImage
  src="https://github.com/mole99/tiny-vga/raw/main/img/demo.gif"
  alt="Tiny Tapeout VGA example on a monitor"
>
  [800x600 SVGA demo](https://github.com/mole99/tiny-vga)
</BlogImage>

The VGA ladder splits each digital RGB signal into two analogue values (six values in total), meaning that it uses the RGB222 color format.

---

In retrospect, I'm incredibly glad to have had this introduction to AV interfaces through this ASIC project, because now I have a few ideas on feasibly adding proper video-out to [Pocketbyte](https://pocketbyte.co).

### Procedural Rendering

At first glance, you might be wondering how there is even enough memory to store a 640x480 framebuffer for the display output. After all, there is only space for ~1000 logic gates.

```
uint16_t fb[640*480]; // ???
```

Well, the neat part is that there is no framebuffer!

Unlike with SPI or I2C displays, where you usually store a framebuffer (and optionally a backbuffer) and manipulate those pixels before pushing physically, VGA uses a sequential scanline-based rendering approach, meaning that we don't need to store any video data.
Instead, we can render sprites, images, shapes, and any other kind of graphical data using just the current coordinates of the beam.

This is known as procedural rendering.

Here's a cut-down example from `renderer.v`:

```
// ...
// Inside the module
// ...

    wire is_player = (
        (h_count >= PLAYER_X && h_count < PLAYER_X + PADDLE_WIDTH) &&
        (v_count >= player_y && v_count < player_y + PADDLE_HEIGHT)
    );

    always @(posedge clk) begin
        if (!video_en) begin
            // Blanking period
            r <= 2'b00;
            g <= 2'b00;
            b <= 2'b00;
        end else begin
            if (is_player) begin
                r <= 2'b11; g <= 2'b11; b <= 2'b11; // Draw the player paddle
            end
        end
    end
```

We check to see if the current beam position is within the boundaries of the player's "sprite." If so, we assign white pixels to draw the paddle. If not, we assign black pixels to draw the background.

The great thing about procedural rendering is that you only need to store two 10-bit registers (`h_count` and `v_count`) to keep track of the current beam position. That means we save 230,397.5 bytes since we forego a framebuffer!

## Controls

The gamepad I/O was very trivial. It's almost exactly the same as working with a microcontroller: you just monitor a specific pin and interpret LOW/HIGH and PRESSED/RELEASED.

This design requires a single push button (or momentary switch) to be connected to `ui_in[0]`, such that it connects to LOW when pressed.

Unlike traditional Pong, where you have both an "up" and a "down" button, this variant uses only a single button. The paddle continuously moves down, and if you want it to move up, you press and hold the button.

## GDS Generation

Just like how CPUs cannot directly read code written in programming languages, manufacturers cannot directly build chips using just HDL code.

Similar to how you need a compiler or an interpreter to get a CPU to understand your code, in order to make your design readable by manufacturers, you must run it though an ASIC hardening flow.

Typically, during this process, the code is synthesized using a tool like [Yosys](https://yosyshq.net/yosys/) (generates logic gate cells from HDL), placed and routed inside allocated tile boundaries, and finally verified using Design Rule Checks and Layout-Versus-Schematic checks.

Luckily, Tiny Tapeout offers an automatic hardening flow based on [LibreLane](https://fossi-foundation.org/librelane), which triggers automatically when pushing to the repository.

This design ended up using exactly 926 cells.
